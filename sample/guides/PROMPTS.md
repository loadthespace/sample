# 플랜/구조화

지금까지 한 인터뷰 기반으로 AGREEMENT.md에 맥락, 제약, 출력 형식 최대한 기입
AGREEMENT.md: 지키거나 하면 안 되는 것들, 문제가 될 만한 것들 등을 제한/제어하는 가드레일 관련 내용 포함
구현 전 예외 사항에 대한 토론
    ex) 한 번에 많은 접속이 있을 때 처리 방법
AGREEMENT.md를 만족하는 구현을 위한 작업을 AI가 다룰 수 있는 단위로 쪼개기
왜 그렇게 구현하려 하는지, 그 방법과 그 기술이 왜 좋은지, 이 방법대로 했을 때 어떤 트레이드오프가 있는지를 물어보기
어떻게 진행하면 좋을지 방향성은 내가 잡되, 그걸 구현하기 위한 flow를 AI한테 여러 개 제안받고, 각 flow는 그게 왜 좋은지 등을 물어보며 이 중 내가 고려하여 선택. 물어볼 것:
    전체 작업을 기능별로 여러 세션으로 동시에 돌릴지, 하나의 세션에서 순차적으로 구현하는 게 나을지
    왜 그렇게 생각하는지
    여러 세션을 동시에 할 경우 어떻게 해야 하는지
    각 세션의 작업 단계를 어떻게 나누는 게 적합할지
    ex) AGREEMENT.md 기준으로 이 웹 서비스를 만들 방법 후보를 3개 이하로 비교해. 코드는 쓰지 마.
        후보마다 표로: 장점 / 단점 / 이 과제에 확실히 맞는 이유 / 조건에 따라 맞을 수 있는 이유 / 확실히 안 맞는 요소 / 조건에 따라 안 맞을 수 있는 요소.
        조건: 180분 안에 완성, 내가 구조를 설명할 수 있어야 함, 서버는 0.0.0.0:8000, 시험 환경에서 설치가 막혀 있을 수 있음.
        마지막에 추천 하나와 그 이유를 3줄로. 추천만 하고 실행은 내 결정을 기다려.
    [프레임이 어느 정도 잡히고] /plan AGREEMENT.md 기준으로 5단계 이하로 나눠. 단계별 산출물과 검증 방법 포함. 아직 수정하지 마.
[멀티 에이전트 시] 구현에 들어가기 전 그 세션들의 에이전트들에게 해당 플랜들을 각자의 관점에서 검토하게 시킴
아래 요구 조건을 만족하게 plan을 짜야 함
    작업 단계가 끝날 때마다 보안, 코드 등을 점검하는 Reviewer 역할 에이전트를 따로 구성할 예정 (구현한 AI한테 질문할 경우 자기 평가에 대해 조금 더 좋게 편향되는 경우가 있으므로)
    이 검증 에이전트를 통해 이 방법이 진짜 좋은지, 이 기술이 이래서 좋다는데 진짜 그게 맞는지, 그러한 장점이 잘 반영된 코드인지 검토시킬 예정
    일방적으로 구현이 진행되면 안 되고, 단계가 나눠져 각 단계별로 구현하면서 나의 코멘트와 함께 진행하는 flow
[데이터가 있을 때] 파일을 수정하지 말고 구조, 행 수, 빈값, 중복, 표기 혼재, 기간을 요약해. 스크립트로 확인하고 결과를 보여 줘.
[예외 처리] 예외나 실패 루트로 갈 경우 (이건 직접 생각, 토의해서 고안. 예외 경우를 다 잡고, 이런 것들이 있는데 이것 외엔 없을지 추가 토의)
    이럴 때 이러면 안 된다. 대신 이렇게 처리한다.
    백엔드 단에서만 알면 안 되고 프론트 단에서도 표기를 해 이해할 수 있도록
    true 조건(성공 루트) 외에 예외 조건 처리, retry 처리. 그리고 백엔드에서의 처리가 프론트엔드에서 보이게
        ex) 입력 파일 없음, 형식 오류 등
[AI 기능이 필요할 경우] API 키는 환경변수에서 읽어. 코드에 직접 쓰지 마.
[입력 칸이 있을 경우] 웹에서 값을 넣어야 하는 칸이 있는 경우 해당 칸에 예시 글자를 반투명 글씨로 두어 어떤 형식으로 입력해야 하는지를 가이드
    (실제 창에 입력된 값은 아니고 보이기만. 글자를 입력하면 예시 글자는 사라짐. 웹에서는 placeholder라고 부름)

# 검증

코드도 직접 열어 보고, 왜 이런 의도로 짰는지 확인 (나온 구현에 담긴 AI의 의사결정/산출물을 이해)
부채 점검 (결정하거나 AI 결과를 받을 때마다)
    이걸 왜 이렇게 했는지 어딘가 적혀 있나? -> 없으면 의도 부채 -> DECISIONS.md 한 줄
    이게 어떻게 동작하는지 내 말로 설명할 수 있나? -> 못 하면 인지 부채 -> 직접 읽거나 Codex에 그 줄만 설명 요청
    필요 이상이거나 깨지기 쉬운 부분은 없나? -> 있으면 기술 부채 -> 빼거나 REPORT 한계에 기록
검증 요청에 따라 수정 후 끝나면 AGENTS.md 내의 커밋 형식을 참조하여 커밋하라고 지시
    커밋할 때 v1, v2, v3 태그를 붙이게 할 것
[동작 검증]
    한 번 검증하고 확인할 때 서버 껐다 켜는 거 잊지 않기
    돌긴 돌겠지만, 내가 원하는 니즈가 정확히 반영된 상태로 구현이 된 건지
    직접 실행해 보고, 이게 내 환경 외 다른 환경에서도(이걸 사용할 이용자 예상 환경) 가능한지 검증 에이전트에게 확인
    정상 루트가 아닌 반례 입력을 10가지 정도 만들어서 적용한 뒤, 어떤 것을 했고 어떤 결과가 나왔는지 확인
내가 요구하지도 않았는데 자체적으로 판단하여 over engineering 하진 않았는지도 체크
    ex) AGREEMENT.md 대비 빠진 것과 과한 것(요구에 없는 기능·구조·의존성) 찾기
다른 방법으로 구현했을 때와 비교했을 때 어떤 트레이드오프가 있는지
사이드 이펙트는 없는지
[데이터가 있을 경우] 수치나 글자 등이 원본 그대로인지
예외 처리 고려한 상황에서 해당 예외 처리가 발생할 만한 모든 상황에서 다 그렇게 발생하는지 에이전트로 검증
검증으로 새 riv마다 HANDOFF.md에 써 둔 양식에 맞춰 지금까지 한 것들 거기에 작성 요구. 기존 것 지우지 않고 append 시키기
